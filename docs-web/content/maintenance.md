# Memory, tiering and reclamation

Native `EngineConfig.memory` separates hot payload (64 MiB), metadata/index (64 MiB), query/staging workspace (64 MiB) and result (16 MiB) limits by default. These are conservative accounted bounds, not measured process RSS. Metadata accounting includes routing and index container allowances; payload accounting uses encoded record sizes. Parser/IO format limits are additional bounds. Large native operations can reject with `limitExceeded` before committing even when their final graph would fit, because staging and index construction need temporary workspace.

Writes share immutable record/index roots and reserve changed tree paths and record values before allocation, then check the final staged state before WAL append. Transaction admission checks temporary work against workspace limits; it does not add that scratch estimate to persistent metadata. Overwrites, deletions and batches whose temporary growth disappears before commit can therefore succeed at the metadata ceiling. The completed staged graph must still fit both metadata and hot-payload limits before any WAL append. Property-index creation and explicit rebuild decode one cold record at a time and preserve residency. The caller query ceiling remains 16 MiB even though native engine configuration has a separate 64 MiB workspace allowance. Posting memberships use immutable sorted blocks of at most 32 keys, with actual block/vector/tree overhead included in metadata accounting. GC reserves a bounded candidate page and streaming reader instead of copying the graph or loading retained catalogs. It adapts the page to the smaller engine/caller workspace ceiling; insufficient workspace rejects before listing or deletion. Query candidate collections and returned records have workspace/result guards; a multi-statement result also has an aggregate cap. Swift query configuration and broader query work/depth budgets are implemented; separate residency configuration remains native. Memory held by caller-owned result copies is outside the engine's residency budget.

## First-release memory policy

Queries, traversal, writes and trim retain their existing accounted-memory limits. These bounds cover the reservations and resident data described above; they are not a hard ceiling on total process memory.

Checkpoint and open/recovery may require additional temporary memory beyond the query and residency limits. The first release does not enforce or promise an aggregate temporary-memory cap for these paths. File-format validation and final residency checks remain in place, but they do not bound all temporary allocations. Applications requiring a strict total-memory ceiling are outside this first-release guarantee.

Production qualification requires checkpoint and reopen to stay within the approved [peak process RSS budget](benchmarks-data.md) for each claimed platform/workload. Sustained tests must also check for growing memory use across repeated operation; see [memory qualification](testing.md#memory-qualification). Passing a workload budget is evidence for that workload, not a runtime allocation limit or a guarantee for arbitrarily larger databases. A dedicated maintenance cap is future work if measurements reveal a problem or an application requires strict enforcement. This policy does not itself qualify a release or deferred hardware.

`trim_memory(targetBytes, context)` on the native engine forces eligible hot payloads toward a target regardless of recent activity. C `graphdb_trim_memory` and Swift `trimMemory`/`handleMemoryWarning` request target zero. A call handles at most the configured sweep batch (default 4,096 records), reports `evicted`, `evictedBytes`, `pinnedBytes` and `unmetBytes`, and can be repeated. An unmet target can reflect pins or the bounded batch. Releasing encoded payload bytes does not promise an equal RSS reduction: metadata, allocator caches and results remain resident.

Native `pin_node` returns an RAII lease preventing that payload's eviction while the lease exists. Snapshots separately hold the operation gate, so trims wait for them. A cold read can return a validated value without promotion when the hot budget is full. Failed payload writes leave the original hot record readable and return an error from explicit trim. The legacy sweep returns a count and may hide per-record errors; use explicit trim for actionable status.

Trim selects one lexically resumed group at a time under the smaller native/caller workspace ceiling, respecting workspace already reserved by the caller. Candidate containers, copied records, codec buffers, filenames/paths and replacement-tree scratch are reserved before allocation. Small budgets reduce group size; a single candidate that cannot fit returns `limitExceeded` before writing it. A zero sweep batch selects nothing. Selection retains no graph root across groups, and final pinned-byte accounting visits records without copying manifests.

Cold manifests are prepared without copying hot properties. Each replacement checks actual metadata capacities against the unchanged metadata limit before publication; filename growth can therefore reject a trim even when its temporary group fits. Limit, cancellation and I/O failures retain the count/bytes of earlier completed evictions. `pinnedBytes` and `unmetBytes` summarize successful calls; error results report the completed eviction prefix. An error can leave unreferenced payload files for ordinary GC. Internal disk backends must explicitly support bounded trim writes; the default rejects before I/O.

Trim performs one initial graph/index accounting scan, then subtracts each successfully evicted record's original payload charge while holding the operation gate. It writes groups of at most 64 immutable payloads, deriving extent/checksum descriptors from the bytes written without rereading them. Every member is synced and the cold directory is synced before any member's residency changes; failed groups keep their hot records readable. On Apple platforms, each member is first `fsync`'d, then one `F_FULLFSYNC` flush persists the group on the same checked storage device. Other POSIX platforms `fsync` each member. Cancellation is checked between writes and residency changes; earlier completed evictions remain valid. The full call still holds the operation gate, so schedule it off the UI thread. Swift async pressure/lifecycle APIs perform this work off the UI actor with request cancellation. Physical-device latency qualification remains incomplete.

TTL uses a monotonic inactivity tick. Logical changes persist wall-clock modification metadata in WAL upserts and checkpointed records; reads and promotions do not increment logical versions. Reopen assigns a fresh monotonic basis, granting loaded hot records a full inactivity interval. Wall-clock changes cannot cause immediate eviction. Clock providers are injectable for deterministic tests. Recovery validates the logical graph first, then spills excess staged hot records to synced immutable payloads before tail repair/publication, so prior trims do not make acknowledged data impossible to reopen under the same hot limit. Failed spill IO preserves existing root/WAL bytes.

## Checkpoint APIs

Swift synchronous `try db.checkpoint()` and asynchronous `try await db.checkpoint()` use the same native maintenance policy as close and suspend. C callers use `graphdb_checkpoint` or request-aware `graphdb_checkpoint_v2`. These maintenance entry points do not apply query workspace or result limits. Explicit NGQL `checkpoint` remains a query command and can fail with `limitExceeded` under the configured query budget even when the maintenance API succeeds.

Async checkpoint checks cancellation and the configured request deadline while waiting for the operation gate and immediately before starting. Once maintenance begins, it finishes the durability protocol and reports its storage outcome; late cancellation does not replace that outcome. It runs off the caller's actor and participates in close/suspend draining. The [first-release memory policy](maintenance.md#first-release-memory-policy) defines the temporary-memory exception and the required workload qualification.

Checkpoints use the currently published catalog as durability evidence for exact unchanged cold references: record kind/identity/label/endpoints/version and payload filename/length/checksum must match. Strictly ordered manifests are compared in linear time with constant comparison workspace; unordered manifests or uncertain catalog provenance fall back to full sync. New or changed references still sync in groups of at most 64 through the same durability primitive. Every required group must finish before catalog creation and CURRENT publication. A failed sync or catalog save cannot establish new durability knowledge; retry re-syncs those new references. Root publication failure retains fencing. Catalog validation, WAL, directory and root sync ordering, retained generations and safety limits remain unchanged.

Payload files are immutable while referenced by Nova's durable generations, and database access requires exclusive ownership. Checkpoint reuse does not inspect already-published payload files; external deletion may therefore stop causing an incidental checkpoint failure. Missing or corrupted payloads still fail authoritative reads and offline integrity checks. Checkpoint is not a full payload integrity scan.

## File lifecycle

```text
write exclusive payload → sync file → sync cold directory → switch residency
trim group: write members → sync every member → shared Apple full flush → sync directory → switch residencies
promote / overwrite / delete → retain old files until unreachable
mark live + current catalog + previous catalog + required WAL → bounded unlink → sync directory
```

C `graphdb_collect_garbage(handle, maxFiles)` and native `collect_garbage(maxFiles, context)` inspect at most 4,096 entries per call and report inspected/removed counts. The workspace may lower the inspected count further. Zero requested files is a no-op after fencing/cancellation checks. Calls advance directory cursors only after marking succeeds; repeated calls converge when writes stop. Cancellation is checked before work and between safe units. Removing an unreferenced file is safe even if interruption leaves its directory sync pending; power loss may restore the orphan.

GC marks both retained catalog generations, live cold manifests and the WAL chain selected by CURRENT while holding the engine gate. WAL mutations contain logical values, not payload filenames. Serialized operations prevent a simultaneous promotion, snapshot, checkpoint or backup from losing a dependency. [Backup](backup-restore.md) holds the same operation gate through destination publication. GC streams the complete current and previous catalogs through a 16 KiB buffer and checks their envelope checksum, extent, version, database identity, generation and LSN against descriptors already validated at open/checkpoint. It does not delete until both scans succeed. Strict catalog loading remains unchanged for open/repair. The legacy native path without Recovery reserves 4 KiB plus 256 times encoded catalog size before strict loading and may reject small budgets. GC removes only reserved Nova-generated names (`payload-<32 hex>.rec`, `catalog-<32 hex>.db`, `wal-<32 hex>.log` and their known temporary forms), and leaves unknown external files alone. Do not place unrelated files in Nova's reserved filename namespace.

Promotion and deletion do not immediately unlink payloads. After the last referencing generation is retired by subsequent checkpoints, run GC to reclaim them. Reclamation is explicit; schedule it when the application can afford directory work. Directory enumeration may scan earlier entries to reach its cursor, while returned entries and removals remain bounded. Swift maintenance reports and ordered lifecycle scheduling are available; device qualification remains later work.
